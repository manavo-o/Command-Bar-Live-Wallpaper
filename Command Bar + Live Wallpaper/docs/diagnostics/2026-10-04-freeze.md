# Extension freeze observed October 4, 2026

## Confirmed observations

- Existing new tab was blank; browser title initially remained `chrome://newtab` and there was no page accessibility document.
- Opening a separate new tab loaded wallpaper/widgets successfully.
- User reports command bar also fails in this state.
- DevTools attached to the affected tab and background view exposed no selected JavaScript context; console had no messages and performance monitor showed no document/heap measurements. DevTools reload did not recover the affected tab.
- Browser recorded `Unchecked runtime.lastError: The message port closed before a response was received` in `newtab.html:0`. This warning does not identify the cause of the freeze.
- Task Manager grouped several new-tab pages and the extension under renderer PID 31027, displaying 101.8% CPU. A separate new-tab renderer PID 31065 displayed 0.0% CPU and 65.2 MB.
- A 3-second native process sample reported 3.2 GB physical footprint and 3.2 GB peak footprint for PID 31027. The process had launched at 16:45:34; sampling occurred at 19:27:29 Central.
- Nearly all main-thread samples were active in Helium Framework; stripped symbols prevent identifying a JavaScript function or distinguishing allocation/GC/rendering precisely.
- Reloading the extension succeeded. A newly opened extension tab rendered normally and opening the command bar through its toolbar action produced populated tab results.
- Old extension tabs temporarily became native browser new-tab pages after extension reload. Reload is recovery, not proof that recurrence is fixed.

## Conclusion and limits

A shared extension renderer entered sustained high CPU and very high memory usage. Its inability to initialize/answer inspector and command messages explains the simultaneous new-tab and command-bar symptoms. The prior brief hidden-tab performance check did not rule out this long-lived failure.

The initiating code path is not yet confirmed. Do not attribute the freeze to a wallpaper decoder, history-index capacity, or the message-port warning solely from this evidence. No speculative code fix or data deletion was performed.

For definitive attribution, record an allocation/CPU profile from the extension process while it is still responsive and reproduce the transition into the runaway state. Include repeated searches, wallpaper changes, and long-lived multiple new tabs as separate scenarios. Correlate the profile with background history-index persistence/storage-change deliveries and page/media allocations. Preserve the large history index while testing.

## Follow-up: reproducible messaging defect and fix

A deterministic reproduction found an unbounded `COMMAND_BAR_VISIBILITY` relay in the command-bar runtime message listener. Extension-page `runtime.sendMessage` notifications are delivered to other extension pages. Each new-tab listener forwarded the same notification, causing two pages to ping-pong indefinitely; three or more pages multiply traffic.

The pre-fix simulation delivered 100 messages between two pages and still had one pending. This establishes a message storm independently of the process sample and is a strong explanation for its high CPU and memory growth. It does not establish a separate retained-JavaScript-object leak or account for every byte of native renderer memory.

Removed the visibility relay; incoming notifications no longer create more notifications. Toggle requests now explicitly acknowledge receipt. Added behavioral tests with five simulated pages and for ping/toggle responses. All 27 tests and syntax checks pass.

Reloaded the installed extension, opened two fresh extension tabs, and invoked the toolbar command-bar action. The command bar populated results and the other new-tab page remained available; neither immediately entered the previous freeze. The tab-strip estimates were about 92 MB per fresh tab. Long-duration memory testing remains pending.

Aggregate live background inspection after recovery showed 7,643 history entries, completed/idle backfill, 634 visit-log URL keys, roughly 6.8 MB JS heap, and 3,460,128 bytes of local storage. Current media is a 3840×2160 video. These recovered-state readings alone cannot characterize the previous frozen heap.
